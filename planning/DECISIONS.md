| 25 | 2026-07-27 | **UI shell = SwiftUI/AppKit + C++ engine** (final) | Stunning look and minimal bloat are the top two priorities; native wins hardest on both. ~5–15 MB bundle vs Qt's 40–60 MB; Apple materials/vibrancy/typography free vs building a visual language from scratch. Zero licensing obligations |
| 26 | 2026-07-27 | View models = plain `@Observable` objects, zero SwiftUI types inside | Any panel re-hostable in AppKit when SwiftUI hits a density cliff. Cheap on day one, expensive to retrofit. Sets macOS 14+ floor |
| 27 | 2026-07-27 | Narrow hand-authored POD facade at the C++↔Swift boundary | No templates, no move-only types, **no exceptions escaping (they terminate the process)**. Only boundary stable across Swift releases |
| 28 | 2026-07-27 | Rejected: C++ webview shells (`webview/webview`, saucer), WebGPU, WebAssembly, Go | Webview canvas layering is fragile and the canvas *is* the app. WebGPU is an abstraction over Metal (no speedup). Wasm is slower. Go has no imaging libraries, cgo overhead, GC in the pixel path |
| 29 | 2026-07-28 | **Clip the mosaic to a single white level after white balance**, in `linearize`, before demosaic | A blown pixel arrives as (S, S, S) and white balance turns it into the gains — magenta on every clipped light. dcraw's default highlight mode; before demosaic because RCD interpolates across an unclipped neighbour and leaves a fringe rather than a clean edge. Costs the headroom highlight reconstruction could have used, which is the right trade: the cast was on every frame, the reconstruction is optional |
| 30 | 2026-07-28 | **A control's readout is its own reset**, colored by whether it has moved | One affordance says which controls are modified *and* what is clickable. A separate change dot in the margin would say it twice, smaller and harder to hit. The base is per photo, not per type: white balance is the camera's reading |
| 31 | 2026-07-28 | **Export converts through ColorSync, tagged sRGB at source** | A chromatic adaptation typed in here is a cast waiting to happen, and ColorSync's definitions are what every other application reads the file against. Tagging the pixels as the destination instead of converting them is how a file opens oversaturated |
| 32 | 2026-07-28 | **Export metadata comes from ImageIO reading the RAW**, not from LibRaw or exiv2 | exiv2 is GPL (#10). ImageIO reads the container's own EXIF/TIFF/GPS blocks, so the export carries what the camera recorded. Orientation is dropped on purpose — the geometry node already applied it, and copying the tag turns the picture twice |
| 33 | 2026-07-28 | **American spelling throughout**, code and docs | The developer's own English. `denoiseColour` is still read from old sidecars |
| 34 | 2026-07-28 | **Edits autosave: coalesced writes plus a flush on `willTerminate` and on resign-active** | `saveDevelop` ran only when switching photos, so open-one-file-edit-quit lost everything. Two triggers because they fail differently: coalescing covers the crash and the logout, `willTerminate` covers the ⌘Q that lands inside the coalescing window. The queued state travels *with* its URL, so a write cannot be misfiled during the ~50 ms a photo switch spends between `current` moving and the decode finishing |
| 35 | 2026-07-28 | **Lens corrections autoscale to keep the frame full** | poly3 pins the corners, not the edges: at k₁ = −0.35 the edge midpoints fetch 325 px past a 6024 px frame and the clamp smears the border column into a band. lensfun, darktable and Lightroom all zoom for this reason. Computed on the host in `pipe/LensGeometry.h` — it is a question about every pixel at once, which a shader cannot answer |
| 36 | 2026-07-28 | **A disabled node's consumers are told it is disabled** | `Pipeline::resolve` walks a disabled node back to the last live producer, which is correct for pixels and wrong for anything read as something other than pixels. `develop_linear` was reading the colour matrix output as log2 luminance and as guided-filter coefficients. Any node whose input carries a *meaning* rather than an image needs a flag, not just a binding |
| 37 | 2026-07-28 | **Every bench probe asserts a magnitude, against its own baseline, and gates the exit code** | "Did this change something" passed for a blacks slider delivering 39% of its effect. Floors are ratios against a reference control on the same frame, so they survive a change of photo. A known defect may be `WAIVED` with a reason string that prints every run — absent from the output is not an option |
| 38 | 2026-07-28 | **The graph's tail is eight bits for the screen and sixteen only around an export** | The drawable is `bgra8Unorm`, so `rgba16f` through the two largest nodes bought precision nothing could display, at 3.0 ms of a 16 ms budget and 383 MiB. Export widens it, reads, and narrows again. The display node dithers (ordered, Bayer 4x4) because geometry resamples its output and quantises a second time, and two roundings of a gradient is where contouring comes from. The bench asserts the two paths agree to better than one 8-bit step |
| 39 | 2026-07-28 | **Intermediates are not aliased, and that is deliberate** | Render-graph resource aliasing would cut 4.2 GiB to roughly 600 MB, but a cached node's output has to stay resident — aliasing and per-node caching are mutually exclusive. The footprint *is* the cache, and it is what makes an exposure drag 3 nodes instead of 28. The answer for smaller machines is the preview-ROI path, which shrinks every intermediate, not aliasing |
| 40 | 2026-07-28 | **Geometry stays a separate node from the display transform** | Fusing them would save ~2 ms, but `geometry.slang` resamples *display-encoded* pixels on purpose: averaging unbounded scene-linear values blooms a specular edge, which is why film and VFX resample in log rather than linear. Fusion forces scene-linear resampling and merges two small shaders into one large one, against the maintainability constraint. Revisit only if the budget gets tight — there is 6.4 ms of headroom |
| 41 | 2026-07-28 | **Grading zones are Gaussian bands on log2(Y/0.18), and the offset scales with luminance** | Linear-luma zones put middle gray at 0.70 shadows, so the shadow wheel graded the whole picture and the highlight wheel was inert. Same partition-of-unity construction as the tone bands, so a photograph has one idea of where its shadows are. Scaling the offset by Y makes a wheel a constant chromaticity shift at every exposure (0.1077 relative chroma at -3 EV against 0.1079 at +3), and makes the deep-shadow clamp that broke zero-sum unrepresentable. `k = 0.25` is derived: saturation = 1.5k/(1+k), so full travel is 30% from neutral |
| 42 | 2026-07-28 | **Bench probes gate on mean absolute per-pixel movement, not on a summary metric** | A grading wheel rotates hue at roughly constant saturation, so mean luma, mean chroma *and* mean saturation each reported a working wheel as doing nothing — three instruments, same blind spot, because a frame mean cancels a rotation. The summary is still printed for insight into *what* changed; movement decides *whether* it did. Floors are half the smaller ratio measured across two very different sample frames, because one frame was not enough — four probes calibrated on a night sky tripped on a lit forecourt |
| 43 | 2026-07-28 | **Orion is open source. Paid distribution is out of scope.** Supersedes the "undecided by choice" position in STATUS's blocked list | Settles the question that gated several others. The existing rule — avoid GPL, dynamically link LGPL — is kept anyway, because it costs nothing today and it is what keeps the decision reversible. LibRaw is dual LGPL-2.1/CDDL-1.0: taking it under CDDL permits static linking, which is the escape hatch if dynamic linking ever becomes awkward for packaging |
| 44 | 2026-07-28 | **Do not redistribute Adobe's `.dcp` profiles, and do not ship RawTherapee's either** | Adobe publishes no redistribution grant for the profiles bundled with DNG Converter, and projects that derive from them tell users to generate their own copies rather than share outputs. RawTherapee's bundled profiles are user-submitted with no stated licence of their own, inside a GPL-3 project. The DNG *specification* is separate and carries a royalty-free patent grant, so writing a DCP **reader** is fine — but any implementation distributed under that grant must carry a notice crediting DNG technology licensed from Adobe. Put it in the about box before any DNG code ships |
| 45 | 2026-07-28 | **OPEN: LibRaw's built-in colour matrices may themselves be Adobe-derived** | LibRaw's `cam_xyz` table descends from dcraw's `adobe_coeff`, whose matrices were widely understood to have been extracted from Adobe DNG Converter. If so, Orion already ships Adobe-derived colour data — the same position as darktable, RawTherapee and every other dcraw descendant, and unremarkable for an open-source project. **Evidence, checked 2026-07-28:** two independent documenters describe the table that way — Doug Pardee's ProjectDcraw notes dcraw was updated "10–14 days after Adobe releases a new version of Adobe DNG Converter", and Elle Stone's annotated dcraw source calls it "the Adobe-dng camera coefficients". Consistent, but still second-hand: no primary statement from dcraw's author was found. Stays OPEN — it would need answering before any change of distribution model, not before the next commit |
| 46 | 2026-07-28 | **A silent +1.2 EV baseline exposure, and base contrast 1.45** | Orion opened a daylight frame 1.3x darker than the camera's own JPEG, which read as flat and washed *and* pushed most of the picture into the grading shadow zone — one root, two complaints. The DNG spec's `BaselineExposure` (tag 50730) is the mechanism, applied silently on open, which is why the Exposure slider still reads 0.00. Value fitted against two independent references over six patches per frame: +1.20 EV / 1.45 is the joint best on both frames that carry signal, and mean error on the daylight frame fell 0.1543 -> 0.0194. LibRaw does not carry the tag for native ARW, so it is measured rather than read. See research/camera-profiles.md |
| 47 | 2026-07-28 | **Bench probe floors are calibrated across three frames, not one or two** | A night sky, a lit forecourt and a bright daylight cityscape. One frame tripped four probes on the second; two frames tripped six on the third — a bright frame genuinely has no deep blacks, little noise and few shadows, so those controls move less in it and that is not a regression. Half the minimum ratio over three very different pictures |
| 48 | 2026-07-28 | **The camera profile gets the DNG spec's HueSatMap stage, applied in linear ProPhoto HSV** | A 3x3 matrix is linear, so it cannot correct an error that only appears where a stimulus is saturated and narrow-band — no consumer sensor satisfies Luther-Ives. Blue sky is the worst case and Orion rendered it violet. The spec's answer is a hue/saturation table, and Orion builds one for real (90 x 25, `ValueDivisions = 1`, spec entry and loop order) rather than special-casing blue, so a `.dcp` reader later is a reader and nothing else. **`ProfileHueSatMapEncoding = 0` requires linear ProPhoto HSV**, not the working space's HSV, or the cells sit at the wrong hue angles the day a real profile loads — the node converts in and out. Table populated by a correction fitted on one hue region against two independent renderings: -8 degrees, saturation x1.05, centred at 250 degrees over a 60-degree half-width. Sky R/B 0.622 -> 0.451 against a target of 0.450. Costs one full-res pass, upstream of exposure, so the gate is unmoved at 9.37 ms p95 |
| 49 | 2026-07-28 | **Lens corrections read lensfun's database, and do not link lensfun** | The maths was never the missing part — the models were already implemented, tested and running on the GPU; what was missing was the measured numbers, and those sit in XML. Linking the library would add an LGPL-3 dependency, a build step and a second implementation of the same polynomials to obtain a value that can be read directly. The database (1,558 lenses) is vendored under `data/lensfun/` unmodified with its CC BY-SA 3.0 licence; attribution and share-alike apply to the data, not to Orion's code. The shader now evaluates ptlens, of which poly3 is the a = c = 0 case, so both of the database's distortion models land in one kernel |
| 50 | 2026-07-28 | **A confident wrong lens profile is worse than no profile**, so matching is conservative | It distorts the frame and reports that it measured it. Names normalize to letters and digits only (which collapses `f/`, case and punctuation), match by containment either way with the longest winning, and are refused below eight characters — `50mm` is inside a hundred entries and identifies none of them. A match on a differently-spelled name is flagged `approximate` and the panel says so. The developer's own Sigma 24mm F1.4 DG DN is not in the database and correctly reports nothing rather than borrowing the DSLR DG HSM entry, which is a different optical design |
| 51 | 2026-07-28 | **A profile replaces the manual sliders rather than adding to them** | Two sources for one coefficient is a control that fights the data: the profile knows what this lens does at this focal length, and a slider on top would be undoing a measurement by feel. The sliders grey out while a profile is on. Chromatic aberration stays manual in both cases — the database's TCA figures are per-copy, sample variation is the same order as the aberration, and a wrong one adds coloured edges |
| 52 | 2026-07-28 | **Exports strip GPS unless asked otherwise** | `ImageWriter` copied the whole GPS block onto every export, and the panel had no metadata control at all — a photo taken at home published the home coordinates to anyone who downloaded it, silently, with nothing in any viewer to say so. Three-way control (keep all · strip location · strip everything), defaulting to strip location, and the default is asserted in the suite because the failure mode is invisible |
| 53 | 2026-07-28 | **The generated design tokens are the palette; the hand-written mirror is deleted** | `DesignTokens.swift` is generated from `design/tokens.json` and nothing imported it — the app re-declared `Palette` by hand, with two constants renamed, one dropped and two invented. The generator also emitted Display P3 while the mirror built sRGB, so the app rendered colours the token file did not specify. Tokens are authored as sRGB hex, which is what the HTML mockup renders and where the palette was judged, so the generator emits sRGB and gains a numeric `Components` enum for the consumers that cannot take a SwiftUI `Color` (the Metal clear colour, the canvas surround) |
| 54 | 2026-07-29 | **Brush masks are reinstated into M4**, reversing the v1 cut recorded in ROADMAP and FEATURES | Asked for directly by the developer. The original cut named three costs — stroke capture, edge-aware snapping, and mask storage — and two of them turned out not to be costs. **Storage is a list of dab centres, not a raster**: a few kilobytes, resolution-independent, and exact under crop or rotation because each centre goes through the same transform the image does, where a raster mask would be 24–120 MB at 24–60 MP and compound blur every time it was resampled. **Edge-aware snapping is the guided filter Orion already has**, built and tested for dehaze — masking.md §4 is a second input binding on it, not a new algorithm. What remains is stroke capture, which is one kernel and the canvas gesture work the gradient overlay just paid for. The kernel and its tests landed the same day the decision was reversed; the interface has not. Recorded rather than quietly built, because ROADMAP and FEATURES both stated the opposite and two copies of "what we are building" disagreeing is finding #14 of the outside review |
| 55 | 2026-07-29 | **One brush node serves all four mask kinds, chained after the gradient rather than replacing it** | The graph cannot swap a node's kernel per render, and writing into a node's output from outside the graph is worse than one extra pass. Chaining works because a pass with no dabs is the identity — a property the suite already pinned, and which is now asserted over *every* pixel rather than one, because that is what the pass-through actually rests on and an off-by-one would surface at an edge. So: kind 0 gradient writes 1.0 and the brush passes it through; kinds 1 and 2 pass the gradient through; kind 3 starts from empty and lays the stroke. ⚠ The risk was never the brush — it is that every existing gradient mask now reaches `develop:linear` through a new node, so the three pre-existing measurements were re-taken and are exact: 0.4703, 0.1981, 0.4110 |
| 56 | 2026-07-29 | **Brush dab centres live outside `Adjustments`; the struct carries only a revision counter** | `Adjustments` is compared field by field on every slider tick to decide what to redirty. Carrying a stroke through that comparison would make every tick walk thousands of points. `DevelopPipeline` owns the list, set through its own facade call, and `brushRevision` — a single int — is what tells `apply` the mask is stale. The trap this creates is real and is documented at both the C and Swift boundaries: change the points without bumping the revision and the picture stops following the hand, with nothing in the code looking wrong. `Engine.setBrushStroke` therefore does both, so no caller has to remember |
| 57 | 2026-07-29 | **The mask overlay is view state, not edit state** | It is how the photographer is *looking* at the picture, not a change to it. So it is deliberately absent from `DevelopState`: it never reaches the XMP sidecar, never enters undo history, and never follows the photo to another machine. `export()` forces it off around the write and restores it afterwards, including when the export throws — an export with the overlay on would write a red-tinted photograph and nothing in the file would say why. ⚠ That guard is correct by construction but has no test |
| 58 | 2026-07-29 | **The landing site is dependency-free static files in `web/`, deployed by GitHub Actions to Pages** | React and Framer Motion were scaffolded and reverted. The page has no interactivity by explicit requirement, so React's state-to-UI core is unused, and no gestures, so Framer Motion reduces to one `IntersectionObserver`. What they would have cost is a build step, a lockfile in a C++ repository, and Vite's `base` trap — the default emits absolute asset paths that 404 on a project page **while the deploy still reports success**. That failure mode already occurred once here via `.gitignore`'s `orion-*.jpg` rule silently swallowing `web/img/*.jpg`: green push, green deploy, every image missing. Rule that came out of it: a green deploy is not proof — verify the page *and every asset* returns 200 |
