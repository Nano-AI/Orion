# Reported: "sliders slow."
#
# Real, and this file is the number behind it. Each `set` is one tick of a drag,
# and every tick renders the whole frame at full resolution and blocks the main
# thread on `commitAndWait` until the GPU is done.
#
# Measured on _PIC8220 (24 MP), 40 distinct values per control, wall clock minus
# the cost of opening the file:
#
#     exposure   9.3 ms per tick    ~110 fps    fine
#     clarity   60.5 ms per tick    ~17 fps     the report
#     dehaze    67.3 ms per tick    ~15 fps     the report
#
# ⚠️ This is not a defect in any one filter. Clarity and dehaze are already the
# subject of `research/local-laplacian.md` and session 2026-07-29f, which found
# dehaze's six rank passes within 2% of each other — there is nothing to fix in
# *one* of them.
#
# ⚠⚠ **THE PARAGRAPH THAT STOOD HERE IS OBSOLETE, AND SO ARE THE NUMBERS ABOVE
# AS A DESCRIPTION OF WHAT A PHOTOGRAPHER FEELS.** It read: *"What is missing is
# the preview path: M1's Interaction epic named degrade-then-refine and it was
# never built, so every tick pays full resolution for a picture the hand is
# still moving. Only the crop tool has a reduced-resolution path."*
#
# It was built. Every canvas gesture arms it (decision #148 re-derived all six
# against the tree), so a real drag has not paid full resolution for some time —
# but this file only ever drove `drag`, which does not arm, so it kept measuring
# and reporting the path nobody is on. Measured 2026-08-03, same frame, same 40
# ticks, both ways in one run:
#
#     control    unarmed              armed               gain
#     exposure    9.4 ms  107 fps      4.5 ms  224 fps     2.1x
#     clarity    56.4 ms   18 fps      4.2 ms  235 fps    13.4x
#     dehaze     79.0 ms   13 fps      6.5 ms  155 fps    12.2x
#
# So the report this file was opened for — *"sliders slow"* — is answered, and
# the answer is not "clarity is expensive". It is that **clarity costs 4.2 ms to
# drag and 56.4 ms to release**, and both numbers matter: the first is the
# gesture, the second is what the photographer waits for at the end of it.
#
# ⚠ **Both are measured below and both must stay.** Reporting only the armed
# number would hide a regression in the full-resolution path that every commit,
# every export and every keyboard nudge still takes; reporting only the unarmed
# number is what made this file describe a problem that had been fixed.
#
# Kept as a measurement rather than a threshold. A wall-clock `expect` fails on
# a busy machine and teaches everyone to ignore it; this prints the cost so the
# story that fixes it has a before to point at.
#
# ─────────────────────────────────────────────────────────────────────────────
# ⚠️ 2026-08-01. **The three numbers above are not a matched set, and chasing
# the dehaze one as a regression cost most of a session.** They were almost
# certainly taken one control per run. This file drags all three in one process,
# in this order, and `clarity` is left at 0.9 when `dehaze` starts — so a dehaze
# tick runs the clarity chain as well, because `clarity:luma`'s input *is*
# `nDehaze_`. Instrumented: exposure 3 nodes, clarity 39, **dehaze 55** (its own
# 16 plus clarity's 39). 67.3 is about what dehaze costs with clarity still at
# zero; it is not what this file measures and never was.
#
# The hunt did find a real defect, now fixed (decision #90): the dehaze chain's
# parameter blocks were re-pushed every tick, and `setParams` dirties the
# downstream subgraph without comparing the bytes, so nine slider-independent
# nodes — six of them full-resolution rank passes — were redone for a value none
# of them read. Paired and interleaved, two rounds: **147.3/146.4 → 102.7/100.6
# ms** and **127.1/120.6 → 87.0/87.7 ms**, with exposure and clarity unmoved in
# the same process. `orion-bench`'s `dehaze drag` invariant is what holds it.
#
# So read a *ratio between the controls in one run*, never a lone figure against
# the header. On this machine one binary has measured 8.97 and 44.53 ms p95
# within an hour.
#
# ⚠️ Which is why it declares its floor. The runner fails any run that asserted
# nothing, because a scenario that measured nothing is indistinguishable from one
# that passed — decision #124. This file is an instrument, not a test, and this
# line is what says so to something other than a reader.
minchecks 0
open samples/_PIC8220.ARW
set exposure 2.6

print one tick of a drag, at full resolution, on a 24 MP frame:
# Unarmed: the full-resolution path, which a commit, an export and a keyboard
# nudge all still take.
drag exposure 2.0 2.6 40
drag clarity 0.3 0.9 40
drag dehaze 0.3 0.9 40

# Armed: what a hand on a slider actually gets, since every gesture arms.
interact on
drag exposure 2.0 2.6 40
drag clarity 0.3 0.9 40
drag dehaze 0.3 0.9 40
interact off
