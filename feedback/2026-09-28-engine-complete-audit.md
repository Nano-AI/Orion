## New, ranked findings

| Rank | Trigger, source path and consequence | Minimum correction; existing assertion and missing execution |
|---|---|---|
| **P2 — creative LUT state depends on photo dimensions** | Load a nonidentity LUT, then open another photo. `Engine.cpp:61-65` reuses a graph for matching image shape; `DevelopPipeline.cpp:128-159` reloads image and paint state but never clears `lutSize_` or the cube texture. The new photo therefore receives the previous photo's LUT. If its shape differs, `Engine.cpp:70-94` constructs a fresh graph with `lutSize_ = 0` (`DevelopPipeline.h:628`), so the LUT vanishes. `app/Engine+Document.swift:66-130` neither reloads nor clears the LUT, and `app/Engine.swift:532` retains the old `lutName` in both cases. The same user action produces different pixels solely because two cameras share dimensions, while the UI name can disagree with the graph. `DevelopOutput.cpp:518-519` makes `lutStrength` alone insufficient to select the look. | Decide whether LUTs follow the session or the photograph, then implement that rule in the shared open path and keep the UI name synchronized. A two-photo check must cover equal and different dimensions, rendered bytes and shown name. `tests_display.cpp:105+` exercises LUT parsing and a single display dispatch; `tests_dng.cpp:510-542` exercises same-file graph reload, neither covers a LUT across photos. The desktop I/O audit raised this lifecycle as an *unresolved question*; this is the concrete shape-dependent behavior. |
| **P2 — a failed LUT upload can leave full and preview graphs divergent** | `Engine.cpp:164-168` changes the full graph before the preview. Each `DevelopPipeline::setCreativeLut` allocates a full `65³ × 4` float upload grid and updates a GPU texture (`DevelopOutput.cpp:530-572`), so the second call can throw after the first succeeds under memory pressure. `CApi.cpp:484-503` attempts to report failure through `guard`, while `app/Engine+Document.swift:18-31` leaves the displayed LUT name at its previous value. A later full render/export can use the new LUT and a drag preview the old one. The prior engine I/O audit separately notes that `guard` itself can terminate if storing an out-of-memory error throws. | Prepare both uploads before changing either graph, or make preview failure an explicit fallback that drops the preview and reports success for the full graph. One fault-injected failure on the second upload should assert status, name and both rendered paths agree. Existing creative-LUT tests exercise successful dispatch and parse errors, not a partial graph update. |
| **P2 — nonfinite tone-curve points cross the C facade** | `CApi.cpp:65-81` promises malformed channels become identity but passes each coordinate through `std::clamp` without `isfinite`. A C caller's `NaN` stays `NaN`; `x <= previousX` is false and the point is accepted. `ToneCurve.cpp:86-123` then fits and uploads a LUT from those values, with a second `std::clamp` that also preserves `NaN`; `DevelopOutput.cpp:61-70` may call two such channels unchanged because `abs(NaN) > 1e-6` is false. The result can poison display pixels or leave a stale curve after an edit. | Reject nonfinite `x` or `y` in the existing `toChannel` loop and use its identity fallback. A single C-facade check with a two-point channel containing `NaN` must assert the rendered identity and that replacing the malformed curve repushes the LUT. The current GPU curve assertions use finite points; this path was not executed here. |
| **P3 — output-sharpen allocation failure leaks its bitmap context** | `ImageWriter.mm:424-449` creates a raw `CGContextRef`, then calls `unsharpMask` at `:437`. That function allocates a kernel and two full-size float planes (`:199-226`). If allocation throws, control skips the `CGContextRelease(ctx)` at `:448`. On a 42 MP memory failure the context may own hundreds of megabytes and remain leaked while the export error is caught by the facade. This is distinct from the already-reported direct-to-destination write hazard. | Wrap this context in the file's existing `CFHolder<CGContextRef>` (or an equivalent local scope guard). A forced allocation failure at sharpening would verify release; no such fault injection was found, and this is not a measured leak. |
