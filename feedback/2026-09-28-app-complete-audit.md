| Rank | Distinct finding and trigger | Smallest correction and check |
|---|---|---|
| **P1 — unsaved edits can be stranded by Trash** | With A open and a failed sidecar write, confirm moving A to Trash. `runTrash` calls `autosave.stop()` but does not inspect its failed `flush` (`app/OrionApp+Files.swift:425,449`); `Autosave.stop` disarms even when `pending` survives (`app/Autosave.swift:102-106,132-150`). `library.trash` then moves the RAW and its siblings (`app/Library.swift:491-516`). The pending write still targets A's **old path**, while its sidecar is now in Trash; a later edit on B replaces that single pending tuple (`Autosave.swift:123`). The edit to A can disappear from both the moved sidecar and the live session. This is a separate caller of the already documented failed-save weakness, and the batch-specific refusal does not cover it. | Refuse Trash while `autosave.isDirty` remains true after flushing the current document. Check a failing sidecar writer followed by confirmed Trash: RAW/siblings stay in place, the owed A edit remains pending, and retry can save it. |
| **P2 — multi-spot state diff replays every new source drag onto the last spot** | When `DevelopDiff.lines` compares a baseline with two or more new spots, its loop emits `spot` for each but uses `b.spots.count - 1` for **every** `spotdrag source` (`app/DevelopDiff.swift:131-137`). The scenario parser uses the supplied index (`app/Scenario+Mask.swift:407-421`); thus the first new spot keeps the engine-chosen source and only the last source is set. `InteractionLog.committed` and scenario state reports call this shared diff (`app/InteractionLog.swift:104,139`; `app/Scenario+Report.swift:306,314`). This is a log/replay fidelity defect, distinct from the already reported spot undo issue. | Emit each new spot's index from `a.spots.count` upward. Check a two-spot diff against a replay with distinct source locations; both must round-trip. |
| **P2 — Photo menu may retain stale selection count and batch title** | `CullActions` carries `selectionCount` and `batchCount` (`app/OrionApp+Commands.swift:334,349`), but its custom equality omits both (`:269-274`). The type explicitly uses equality to tell SwiftUI whether focused menu data changed. Selecting 4 photos instead of 1 while keeping the same focused URL/rating/tab can compare equal, leaving “Export 1 Selected…” and the Deselect title or enablement stale even though `runBatchExport` reads the live target list. | Include both counts in equality. Check selection growth/shrink at a fixed focused photo and assert the File and Photo menu labels update. A static menu-presence screenshot does not exercise this. |
| **P2 — failed preset deletion is silent in the panel** | `PresetStore.remove` mutates its in-memory list before `save()` and returns `false` on write failure (`app/Presets.swift:332-337`). The Presets row discards that result (`app/DevelopPanels+Presets.swift:83-86`), so the preset vanishes now and reappears next launch with no error shown. This is narrower than the known sidecar save hazards. | Handle the existing Bool and `lastFailure` in the button, or roll back the in-memory removal on failure. Check a read-only preset file: delete reports failure and does not claim persistence. |
| **P2 — failed detected selection leaves an empty mask row** | `addDetected` and `addDetectedInto` create and commit a kind-4 row before calling `findMatte` (`app/DevelopPanels+Mask.swift:180-204`). `findMatte` can throw `nothingFound`/Vision errors or fail the raster write (`:53-92`); its catch only reports a message. The newly added empty row remains in the edit and history, contrary to the menu's promise that choosing Subject/Person/Sky adds **and fills** it. This does not replace the existing async wrong-photo finding. | Generate first, then add/fill/commit the intended row after checking photo and destination identity. Check a no-subject frame: existing rows, sidecar state and history are unchanged. |
